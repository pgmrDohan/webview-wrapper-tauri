# WebView Wrapper Tauri - Design Document

## Overview

A universal Tauri v2 WebView wrapper template that allows web developers to build native mobile apps (Android + iOS) from their existing websites. Developers fork this repo, configure native features via GitHub Actions workflows, and get a fully functional native app with selected plugin capabilities — all without modifying Rust code directly.

## Design Decisions

### 1. Code Generation Approach

The `src-tauri/` directory is treated as a **build artifact**. The source of truth is `config/` + `templates/`. At build time, `scripts/generate.py` reads the config and renders templates into the actual Tauri project files. This means:

- Developers never touch Rust code
- Plugin combinations are validated at generation time
- The same config can be used across CI and local development

**Note**: The existing `src-tauri/` files (Cargo.toml, lib.rs, tauri.conf.json, capabilities/) will remain in git as the **base/default** state. The generate script modifies these files in-place during the build workflow. This allows the repo to remain a valid Tauri project at rest.

### 2. Workflow Splitting Strategy

GitHub Actions `workflow_dispatch` supports max 25 inputs per workflow. With 30+ plugins and their options, we split into:

| Workflow | Purpose | Input Count |
|----------|---------|-------------|
| `setup-common.yml` | App name, URL, identifier, version, etc. | ~8 |
| `setup-plugins.yml` | Official plugin on/off toggles | ~20 |
| `setup-plugins-community.yml` | Community plugin on/off toggles | ~10 |
| `setup-plugin-options.yml` | Per-plugin detailed settings | ~15 |
| `setup-file-association.yml` | File association config | ~8 |
| `setup-signing.yml` | Signing metadata + validation | ~6 |
| `build.yml` | Final build trigger | ~3 |

### 3. Plugin Registry

Each plugin is defined in a central registry (`scripts/plugin_registry.py`) containing:

```python
{
    "id": "geolocation",
    "crate_name": "tauri-plugin-geolocation",
    "crate_version": "2",
    "plugin_init": "tauri_plugin_geolocation::init()",
    "capabilities": ["geolocation:allow-check-permissions", "geolocation:allow-request-permissions", "geolocation:allow-get-current-position", "geolocation:allow-watch-position"],
    "ios_plist": {"NSLocationWhenInUseUsageDescription": "configurable"},
    "android_permissions": ["android.permission.ACCESS_COARSE_LOCATION", "android.permission.ACCESS_FINE_LOCATION"],
    "requires_options": True,
    "category": "official"
}
```

This registry drives both the generate script and the workflow definitions.

### 4. IPC Communication Pattern

WebView apps communicate with native features via `window.__TAURI__` (enabled by `withGlobalTauri: true`). The documentation provides exact JS code for each plugin. Example pattern:

```javascript
// Check permission → Request if needed → Use feature
const { checkPermissions, requestPermissions, getCurrentPosition } = window.__TAURI__.geolocation;
let perms = await checkPermissions();
if (perms.location === 'prompt') perms = await requestPermissions(['location']);
if (perms.location === 'granted') {
    const pos = await getCurrentPosition();
}
```

### 5. Signing Strategy

Actual secrets (keystore files, certificates, passwords) are stored in GitHub Secrets. The setup-signing workflow:
1. Takes non-secret metadata as inputs (team ID, key alias)
2. Saves metadata to `config/signing.json`
3. Validates that expected secrets exist
4. Provides clear error messages listing which secrets to configure

### 6. Build Matrix

The build workflow uses a matrix strategy:
- **Android**: Runs on `ubuntu-latest`, uses Android SDK/NDK
- **iOS**: Runs on `macos-latest`, uses Xcode

Both jobs run `scripts/generate.py` first, then `tauri android build` / `tauri ios build`.

## Error Handling

- **Invalid config**: Generate script validates config against schemas before generating files. Exits with clear error message.
- **Missing secrets**: Build workflow checks for required secrets existence before expensive build steps.
- **Plugin compatibility**: Registry includes platform support flags. Generate script warns if a plugin doesn't support the target platform.
- **Build failures**: Workflow captures build logs and attaches them to the failed run.

## Testing Strategy

- **Unit tests**: Generate script has tests for each plugin combination
- **Integration tests**: Full generate → validate cycle with sample configs
- **E2E**: Actual build workflow runs with minimal config to verify pipeline works
- **Schema validation**: All config files validated against JSON schemas

## Future Considerations

- Project name (`webview-wrapper-tauri`) may change — all references use config values, not hardcoded names
- Additional plugins can be added by extending the registry
- Desktop platform support could be added later by extending the build matrix
- Auto-update plugin could be integrated for OTA updates
